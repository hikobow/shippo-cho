## 目的
犬・猫・鳥・小動物を横断して、飼育希望者に助言するための参照資料。
クロ（Claude）とアイ（ChatGPT）が同じファイルを読んで同じ前提で推論できるようにする。
将来RAG（検索拡張生成）に移行する場合は、下記の「1情報＝1ブロック」をそのまま検索単位にできる。

## 読み方ガイド（クロ・アイ共通。特に、長いファイルを一度に読めない場合）
1. まずこのREADMEと、data/07_principles.md（判断原理）を読む。
2. 相談の内容に合わせて、必要なファイルだけを読む。
   - 犬: data/01_dogs.md（犬種ごとのブロックから、必要な犬種だけ）
   - 猫: data/02_cats.md ／ 鳥: data/03_birds.md ／ ハムスター: data/04_hamster.md ／ モルモット: data/04_guinea_pig.md
   - 保護犬・保護猫、先天性疾患: data/09_rescue_congenital.md
   - 住まい、飼い主の年齢・家族・働き方: data/05_housing.md、data/06_owner.md
   - 動物種を横断して比べるとき: data/00_cross_comparison.md
   - 根拠が薄い点・確認が必要な点: data/08_unverified.md
3. 回答の根拠には、読んだファイルの番号と、判断原理の番号（P1〜P11）を書く。
4. 仮想実例の検証の進め方は、verification/10_verification_spec.md。ユキさんの評価と修正候補は、verification/11_verification_log.md。

## 1情報＝1ブロックの書式
```
### [動物種/テーマ] 項目名
- 内容: 要点を自分の言葉で短く（出典の文章を写さない）
- 出典: 発行者名・ページ名
- URL:
- 情報の性質: 獣医師監修 / 学校・団体の解説 / 保険会社の解説 / 個人ブログ / 行政資料 / 研究論文 / ユキさんの経験
- 信頼性: A / B / C / D（下記）
- 更新日: 出典の公開日または最終更新日。不明なら「記載なし」
- 取得日:
- 対象範囲: 種・年齢・環境
- タグ: #鳴き声 #集合住宅 など
- 見解の割れ: あれば両論併記し、勝手に統合しない
```

## 一次データ（01〜04、09）の実際の書式
ひな形の「1情報＝1ブロック」は、情報が増えた段階で次の簡略形に変えた。
- 動物種（犬種・猫種）ごとに1つのまとめブロックを作る。
- 各項目（性格・寿命・吠え・手入れなど）の末尾に出典番号[1][2]を付ける。
- 出典一覧（発行者・URL・更新日・監修者）は各ブロックの末尾に置く。
- 出典に書かれていない項目は「未確認」と書く（「ない」の意味ではない）。
- 食い違いは「（食い違い）」「見解の割れ」と明記し、統合しない。08のBにも集約する。
- 将来RAGにする場合は、項目の行（出典番号付き）を1つの検索単位に分割して使える。
- 2026-10-06の追加調査分は、各ファイル末尾の「追加調査」にまとめ、出典番号に[B][C][D][E]の記号を付けて既存の番号と区別した（09は番号のみ）。
- 数値と記述は取得時点の自動要約で、原典との照合は未実施（08のA参照）。

## 信頼性ランク
- **A（確立）**: 研究論文や行政資料など、複数の信頼できる出典で一致
- **B（通説）**: 獣医師監修や専門機関の解説で一般的。研究の裏付けは未確認
- **C（経験則）**: ユキさんの臨床経験に基づく。文献に明記なし
- **D（未検証）**: 仮説。ユキさんの指示（2026-10-06）で、データベースには載せない。C（経験則）は利用してよい

## 運用ルール
1. 出典の文章は書き写さない。要点だけ自分の言葉で書く
2. 個人ブログ・体験談は、単独ではCに留める。D（未検証）は載せない
3. クロとアイの見解が割れたら両論併記し、「要すり合わせ」と記す
4. 更新したら、ファイル冒頭の版と日付、およびこのREADMEの「現行版」を記録する（Gitの履歴にも自動で残る）。更新はクロがリポジトリに書き込む。アイは読むだけで、ユキさんが相手側に渡す作業は不要になった
5. 根拠が見つからない項目は、埋めずに08へ移す
6. 費用は扱わない（ユキさんの指示、2026-10-05）。ただし06の「費用」の節は、飼い主の経済面の背景として残す（08のA参照）
7. 範囲は、ユキさんの経験がある動物（犬猫、小鳥、ハムスター、モルモット）。大型インコ・その他は対象外。ウサギは経験者向けのため記載しない（2026-10-06）
8. ファイル名には版を入れない（README.mdとdata/・verification/内の英数字名で固定）。版は各ファイル冒頭の「版:」の行と、このREADMEの表で管理し、過去の版はGitHubの履歴で確認する。古い版のファイルを別に残す必要はない
9. 検証中の仮想実例（事例本文、作成者の想定ポイント、回答）は、両者の回答とユキさんの評価がそろうまで、リポジトリに置かない（独立回答を保つため。verification/10参照）
